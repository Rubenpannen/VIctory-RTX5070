# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A fork of VIctory (via avatarmanz/VIctory-7900XTX, gone from GitHub since 2026-11, and fxceless/victory-fork): a compatibility
layer that runs an Xbox Series title's x86-64 code unchanged inside our process on Windows,
supplying the console platform underneath it. This fork's goal is speed on an **NVIDIA RTX 5070
(12 GB) in a 64 GB PC** (Ryzen 9 5900X; 32 GB of RAM until 2026-11-26, so 12 GB of VRAM and the CPU
are the limits, not host memory); the parent fork was tuned on an AMD RX 7900 XTX (24 GB, 64 GB RAM), so its
measurements in `docs/findings.md` are of that card. Windows-only (`x86_64-pc-windows-msvc`).

## Rule #1: the asset policy

**Nothing from the game is ever stored in this repository** (no assets, shader dumps, disassembly,
extracted tables, screenshots, logs with game data). Read `docs/asset-policy.md` before adding any
file or test data. Consequences for code:

- `.victory-root` marks the tree; anything writing derived data must call
  `victory_core::ensure_outside_repo`. Game, cache and data paths come from `victory.toml`
  (git-ignored, copied from `victory.example.toml`) or `VICTORY_GAME_DIR` / `VICTORY_CACHE_DIR` /
  `VICTORY_DATA_DIR` / `VICTORY_TEST_TITLES`, and must lie outside the repo.
- `cargo xtask policy` is an allowlist: allowed file types only, each under 640 KiB, no binary data,
  no long hex/base64 runs. Exceptions need an entry with a reason in `xtask/src/policy.rs`
  (the only one is `crates/victory-formats/src/bcpack-tables.bin`).
- Patches of the title's code may hold the title's bytes at the places they change (compared before
  patching) and notes on that code, by the owner's decision of 2026-11-26; they belong in
  `crates/victory-game` only (`descriptor_sites.rs`, `frame_rate.rs`, `resolution.rs`).
- Tests that need real game files take paths from env vars and skip when unset; they assert on
  properties, never snapshots. Synthetic test data must be generated by our own code.

## Commands

The toolchain is pinned in `rust-toolchain.toml`; MSVC build tools are required.

```powershell
cargo xtask install-hooks                                  # pre-commit runs `cargo xtask policy --staged`
cargo build --locked --profile diag -p victory --features diagnostics   # target\diag\victory.exe, the build measurements are of
cargo build --locked --release -p victory                  # target\release\victory.exe, no debugging aids
cargo clippy --workspace --all-targets --locked -- -D warnings
cargo clippy --workspace --all-targets --all-features --locked -- -D warnings   # CI checks both
cargo test --workspace --locked                            # needs no game data; includes the policy check
cargo test --workspace --all-features --locked -- --test-threads=1   # diagnostics tests, as CI runs them
cargo test -p victory-shader --lib --locked <name> -- --test-threads=1   # one shader test
cargo xtask policy                                         # asset-policy check by hand
```

- Shader tests validate DXIL with `dxil.dll` (newest Windows SDK, or `$env:VICTORY_DXIL`). An old
  SDK validator rejects `ps_6_6`; point `VICTORY_DXIL` at a current DXC release.
- `crates/victory-gpu/tests/replay.rs` only builds with `--features diagnostics` and needs a real
  D3D12 adapter; `replay_big.rs` has an `#[ignore]`d test that needs gigabytes of VRAM and disk.
- A rebuild of the diag binary after a change in `victory-gpu` or `victory-shader` takes 8-10
  minutes (thin LTO). `.claude/skills/run-victory/smoke.ps1` builds it and checks that the CLI
  answers (`config`, a read-only `inspect`) without ever starting the title.
- Formatting: `rustfmt.toml` (max width 100). The workspace lints deny `unsafe_op_in_unsafe_fn`
  and `unused_must_use`; a few clippy style lints are allowed in `Cargo.toml` for this fork.

Running the title: `scripts\play.ps1 -Exe <title exe>` sets this fork's set of `VICTORY_*`
switches (clearing other `VICTORY_*` vars except the path ones) and runs
`target\diag\victory.exe run <exe> --execute` from the repo root, where `victory.toml` is looked for.
`-Safe` drops the newest switches, `-RayTracing` sets `VICTORY_BVH_BUILDER=1`, `-Display` sets
the title's output size (`VICTORY_OUTPUT`, 2560x1440 by default), `-RenderScale` its upscaler's scale
(`VICTORY_RENDER_SCALE`, 1.0 by default), `-Console series-x|series-s` the console the title sees,
`-Build diag|release` the binary, `-More @{...}` adds switches, and `-Log` / `-LogFile <path>` also
write the log to a file (under the data folder by default; it holds the title's data, so the script
refuses a path inside the repo). Ahead of a run: `victory shaders <archives>`
(translate every shader into the cache) and `victory warm --used` (pre-build host pipelines for the
driver's cache). Other subcommands (`inspect`, `census`, `translate`, `replay`, `config`, ...) are in
`apps/victory/src/main.rs`.

## Architecture

See `docs/architecture.md` for the diagram. The data flow:

- **`victory-loader`** prepares, maps and binds the title's PE image and its DLLs, sets up TLS
  (an exe's static TLS is slot 0; loads are redirected when mapped as a DLL) and installs the
  crash reporter (`crashes.log` in the data folder, faults named `module+rva`). `victory-pe` is
  read-only PE/import-lib analysis.
- **`victory-hle`** implements the console APIs. Import resolution order per `dll!function`: our
  implementation in `victory-hle::modules` (always wins) → host function if `HostPolicy` allows that
  DLL → export of a DLL shipped beside the title → generated stub (`--unimplemented trap|zero`).
  `modules::files` rewrites console virtual-drive paths to host folders; `QueryApiImpl` hands out
  runtime objects (`modules::xgameruntime`). Online areas answer as an offline console.
- **`victory-gpu`** (by far the largest crate) maps D3D12.X objects, command lists and GPU memory
  onto host D3D12. The core problem (see `docs/findings.md`, "The one idea behind most of it"): the
  console shares memory between CPU and GPU, the host does not, so every cost is *noticing* title
  writes (write watch, page guards), *noticing* shader writes (hashes on the card, CPU compares),
  *moving* them, and *waiting* until order is safe. `host/` holds the submission side (preparing
  thread, card steps, landing, traffic), `list/thin.rs` the recorded-not-executed list calls,
  `replay/` the frame recorder and replayer (`docs/replay.md`), `ambient.rs` the stand-in for
  ray-traced light.
- **`victory-shader`** recompiles console GPU code (GFX10, `gfx10/`) to DXIL: `ir::build` makes SSA
  one instruction per machine instruction, `structure` removes EXEC masks, `resource` traces
  descriptors back to root parameters, `emit/` writes DXIL (including emulated ray/box and
  ray/triangle tests; see `docs/fork-ray-tracing.md`). Shaders are translated when the title creates
  a pipeline, from the bytes it passes; ahead-of-time translation is only a warm-up. The shader cache
  is keyed on `victory_shader::TRANSLATOR_VERSION` (**bump it with any change that changes a
  translation**: cached ones are otherwise served as they are; `victory shaders` reports those that
  came out different) plus the switches that change a translation (`KEYED` in
  `victory-gpu/src/shader_cache.rs`; add new ones there, a test checks). Translation depends on the host's largest
  wave size (`emit::lower::host_max_wave`, from the device at run time; `VICTORY_HOST_WAVE=32` for
  offline `translate --warm`). NVIDIA has 32-lane waves only, so the console's wave64 programs take
  the 32-lane forms (`VICTORY_WAVE_WIDE` and the other wave switches pick them).
- **`victory-formats`** (texture tiling/detiling, BCPack, XMA/Opus), **`victory-pipeline`**
  (converter trait, content-addressed cache) and **`victory-game`** (the one title-specific crate:
  formats, build identities, the patches of the title's code that `apps/victory/src/run.rs`
  applies at load) handle data. Everything except `victory-game` is platform-level.
- `tests/fixtures/hle-probe` is a stand-in "title" built from our own code for loader tests.

## Conventions in this fork

- **Runtime switches are `VICTORY_*` environment variables, documented in a comment where each is
  read.** New speed work usually lands behind a switch, off by default or with `=0` restoring the
  old way, so it can be A/B'd. Debugging switches are compiled in only with the `diagnostics`
  feature. Upstream's list of debugging switches is in `docs/README-fxceless.md`. In `victory-gpu`,
  on/off switches go through `switch::on`, and diagnostics builds can flip switches mid-run with
  `VICTORY_AB=<seconds>,<switch>,..` (`ab::pick`) to measure both sides in one scene.
  `SWITCHES.md` is the table of every switch (description, default, values, whether `play.ps1` sets
  it); it is kept by hand, so add or change its row with the switch (the comment where the switch
  is read wins where they disagree). xtask's test
  `documented_switches_are_read` fails if a Markdown file names a `VICTORY_*` switch that no Rust
  file reads as a quoted literal of its whole name.
- Code that approximates the console is marked `shortcut:`.
- Commit messages are plain-language sentences describing the behaviour change and the switch that
  controls it; work taken from other forks names the source commit and author
  (e.g. "(from Belobug 84ea9c12, romainhedouin)").
